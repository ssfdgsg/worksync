## 5. 当前阻断问题

### E2E-002A：`restic copy` 参数与 restic 0.18 不兼容（P1）

worksync 当前执行：

```text
restic copy SNAPSHOT -r REMOTE --quiet
```

环境中的 `RESTIC_REPOSITORY` 指向本地仓库。restic 0.18 将 `-r REMOTE` 视为主/目标仓库，并要求显式提供源仓库，实际错误：

```text
Fatal: Please specify a source repository location (--from-repo or --from-repository-file)
```

正确方向是明确区分目标与源，例如：

```text
restic -r REMOTE copy --from-repo LOCAL SNAPSHOT
```

pull 方向同理，并需要分别处理目标密码与 `RESTIC_FROM_PASSWORD`。

### E2E-002B：restic 跨仓库 copy 会改变 snapshot ID（P1）

这是比参数错误更根本的问题。

手工按 restic 0.18 正确参数从本地复制到真实远端 SFTP 仓库后：

- descriptor 中的本地 ID：`628528ec80ac...`
- 远端生成的新 ID：`4587d9dd03f7...`
- 远端 snapshot JSON 仅用 `original: 628528ec80ac...` 记录来源。

当前 descriptor 固定保存 `restic:628528ec...`。push 后远端没有这个 ID；pull 再按旧 ID选择 snapshot 会复制 0 个对象或失败；即使成功 copy 到第三个仓库，ID 还可能再次变化。

建议不要把某一仓库内部的 restic snapshot ID 当成跨仓库稳定内容地址。可选方向：

1. 不使用 `restic copy`，直接同步同一加密仓库的 pack/index/snapshot 对象，保持 ID 不变；或
2. push/pull 维护每一跳的 snapshot ID 映射，并生成目标端 descriptor；或
3. 将 volume 快照导出为自有内容寻址对象，restic 只作为本地实现细节。

### E2E-008：首次 `up` 未创建 managed volume 宿主目录（P1）

干净 data root 首次执行 `up`：

```text
Error: statfs .../workspaces/workspace: no such file or directory
```

手工 `mkdir -p` 后立即成功。`buildCreateSpec` 创建了 data root，却没有为每个 managed volume 创建最终 host path。

建议在 Podman create 前逐个创建 managed volume 目录，并验证它位于 backend data root 内。

### E2E-009：fresh clone 未初始化本地 restic 仓库（P1）

全新 clone data root 执行 `fetch origin`，在将远端 snapshot copy 到本地仓库时失败：

```text
Fatal: an empty password is not allowed by default
```

目标路径下没有 restic repository。手工 `restic init` 后才能继续。pull/fetch 应在 copy 前对本地仓库执行 `InitIfAbsent`，并正确提供 source/destination 两套凭据。

### E2E-010：fresh clone rollback 缺少 projects row（P2）

fresh clone 完成 fetch/pull 后执行 `rollback latest`，在镜像 load 后失败：

```text
constraint failed: FOREIGN KEY constraint failed (787)
```

原因是 checkout row 引用 project，但 fetch/pull/rollback 没有先写入 projects row。执行一次 `up`（即使后续 create 失败）登记 project 后，该外键错误消失。

建议所有 project-scoped 命令统一在持锁后调用 `ensureProjectRow`，或让 project discovery 统一负责登记。

### E2E-011：部分 fetch 会被误判为本地已完整（P1）

首次 fetch 在 descriptor 已下载、restic snapshot 未完成时失败。`LocalHasCommit` 只检查 descriptor 文件存在；重试时可能停止下载依赖并将提交视为完整。

本轮测试中，经过测试层参数绕行后 `fetch` 输出成功，但本地 restic repository 的 snapshots 仍为空，随后 rollback 报 snapshot 文件不存在。

建议：

- descriptor 先写 staging；所有 OCI/restic 依赖验证成功后再原子发布。
- `LocalHasCommit` 改为完整性检查：descriptor digest、OCI archive/blobs、所有 snapshot 引用都必须可解析。
- pull 推进 ref 前再次执行依赖完整性验证。

## 6. 建议修复顺序

1. 先决定 restic snapshot 的跨仓库身份模型，解决 E2E-002B；只修 CLI 参数仍无法闭环。
2. 修复 E2E-002A、E2E-009、E2E-011，确保传输、初始化和原子发布一致。
3. 修复 E2E-008，让全新安装首次 `up` 可用。
4. 修复 E2E-010，让 fresh clone 能直接 pull → rollback → up。
5. 再跑一次完全无手工目录、无参数 wrapper 的双数据根 E2E；验收条件是 rootfs 和 tracked workspace 两个标记同时恢复。

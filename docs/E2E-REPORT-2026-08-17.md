# worksync E2E 测试报告（2026-08-17）

## 1. 结论

本轮使用真实 Podman Machine、真实 restic、真实 SSH/SFTP 协议进行测试。基础容器生命周期、host workspace 挂载、本地 commit、OCI 导出、restic 本地快照、环境-only 的 SSH push/fetch/pull 均可工作；但“完整工作区跨机同步并恢复为可运行开发环境”的主链路尚未闭环。

发布判断：**不建议按完整同步产品发布；可作为本地生命周期和对象传输原型继续开发。**

阻断主链路的问题：

1. 带 volume 快照的 SSH push 因 restic SFTP 地址格式错误而失败。
2. pull/rollback 虽然成功下载并加载提交镜像，后续 `up` 仍使用 manifest 的基础镜像，提交过的 rootfs 没有被采用。
3. rollback 只覆盖快照中存在的文件，不删除提交后新增的文件，不满足精确工作区回滚语义。

## 4. 缺陷明细

### E2E-001：恢复后的环境镜像未用于重建容器（P1）

复现：

1. 在源容器 rootfs 创建 `/E2E_ENV_MARKER`。
2. commit 并通过 SSH push。
3. 使用全新的 data/config 目录 fetch + pull。
4. 执行 `rollback latest`，日志显示 `loading environment image...`。
5. 执行 `up`，再读取 `/E2E_ENV_MARKER`。

实际结果：`cat: can't open '/E2E_ENV_MARKER': No such file or directory`。

根因方向：`cmdRollback` 只执行 `podman load`；`provisionContainer`/`buildCreateSpec` 随后仍从 `proj.Manifest.Container.Image` 解析并创建容器，没有记录或消费目标 commit 的 environment image。

建议：把“当前 checkout/rollback 的环境镜像引用”作为项目运行状态持久化；`up` 优先使用该 digest，并在 manifest 发生显式变更时定义清晰的失效规则。

### E2E-002：restic SFTP URI 的端口/路径格式错误（P1）

复现：远端为 `ssh://dev@127.0.0.1:22991/...`，本地 commit 含 workspace restic snapshot，执行 `push origin`。

实际结果：restic 子进程连接 `127.0.0.1:22`，失败信息为 connection refused。

根因方向：`internal/transport/remote/store.go` 的 `sftpRepo` 生成 `sftp:user@host:port/path`。该字符串没有按 restic 的 SFTP backend 语义表达自定义 SSH 端口。

建议：使用 restic 支持的 URI/SSH command 形式，并增加“非 22 端口 + 空格路径 + IPv6 host”的真实集成测试。

### E2E-003：rollback 不是精确快照还原（P1）

复现：commit 后修改 `HOST.txt`，并新增 `DRIFT.txt`，然后 `rollback v1`。

实际结果：`HOST.txt` 被恢复，但 `DRIFT.txt` 保留。

根因方向：restic restore 将快照内容恢复到目标目录，但没有先构造干净目录并原子替换，也没有删除快照外文件。

建议：恢复到同文件系统 staging 目录，验证 snapshot 后原子交换目录；对 host source volume 默认先生成备份/确认，避免不可逆覆盖。

### E2E-004：rollback 后状态库保留已删除容器（P2）

实际结果：rollback 已 stop + rm Podman 容器，`status --json` 仍返回旧 ID 和 `State: running`。

根因方向：`cmdRollback` 删除运行时容器后没有删除或更新 `containers` 表。`status` 也只展示 DB 派生状态，没有与运行时对账。

建议：rollback 删除容器后同步删除 container row；`status` 可增加低成本 inspect/reconcile 或明确显示 `unknown/stale`。

### E2E-005：动态 expose 只写 DB，未进入 Podman create spec（P2）

实际结果：`worksync ports` 显示 `port-8080 127.0.0.1:10242 -> 8080/tcp`，但 `podman ps` 只显示 manifest 中的 `10240 -> 3000/tcp`。

根因方向：`cmdExpose` 将动态端口写入 DB；`restartForPorts` 再调用 `resolvePorts(proj.Manifest, existing)`，该函数只遍历 manifest ports，忽略 DB 中额外的动态端口。

建议：合并 manifest 声明和动态 port records 后生成 concrete create spec；同时对重建失败做 DB 事务回滚。

### E2E-006：状态漂移时 `up` 启动错误的容器 ID（P2）

现场：Podman 中按名称存在 `worksync-realtest`，状态库却保留旧 `workbox-realtest` 的已失效 ID，配置摘要相同。

实际结果：`up` 因 `podman object does not exist: <old-id>` 失败。

根因方向：`cmdUp` 先按新名称判断容器存在，但在 config digest 相同时直接启动 DB 的 `ContainerID`，没有确认该 ID 就是按名称找到的实际容器。

建议：按确定性名称 inspect 并以实际 ID 修复派生状态；名称、label、project ID、config digest 必须一起校验。

### E2E-007：`rm` 不能删除运行中的容器（P2）

实际结果：`worksync rm` 返回 `cannot remove container ... as it is running`；先 `stop` 再 `rm` 才成功。

根因方向：`cmdRm` 直接调用 `rt.Rm`。

建议：`rm` 内部先 stop 再 rm，或显式要求 `--force`；CLI 文档和行为保持一致。

## 5. 其他观察

- `up`、`expose` 等涉及 Podman Machine 的操作偶尔耗时 60 秒以上；当前 project lock context 为 2 分钟，网络较慢时容易触顶。
- 默认 agent 是 shell idle loop，Podman stop 最终显示 exit code 137，说明优雅停止信号处理仍可优化。
- `remote list` 当前不受支持，但无参数错误信息仍固定显示 `remote add` usage，CLI 可用性一般。
- 本轮没有修改产品实现代码；工作区原有的未提交改动保持不变。

## 6. 建议修复顺序

1. 修复 E2E-001，打通“pull/rollback → up 使用目标环境镜像”。
2. 修复 E2E-002，打通带 workspace snapshot 的真实 SSH push/pull。
3. 修复 E2E-003，明确并实现精确回滚语义。
4. 修复 E2E-004/E2E-006，建立 DB 与运行时的统一 reconcile 流程。
5. 修复动态端口和运行中 `rm`，再补一轮完整回归 E2E。

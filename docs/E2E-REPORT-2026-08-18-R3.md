## 5. 新缺陷

### E2E-012：正常 fast-forward 的直接 pull 被误判为冲突（P1）

前置状态：

- source local latest：`sha256:1b1bd...`
- remote latest：`sha256:3a50e...`
- remote commit 的 parent 确实是 local latest。

直接执行：

```text
worksync pull origin
```

实际结果：

```text
WB_CONFLICT: local sha256:1b1bd is not an ancestor of remote sha256:3a50e; commit locally first
```

随后执行：

```text
worksync fetch origin
worksync pull origin
```

pull 成功。这证明 commit 链本身正确，问题在校验顺序。

根因方向：`pullFetch` 在 `PullDownloads` 之前调用 `isDescendant`；远端 head descriptor 尚未进入本地 DB，祖先遍历无法从 remote head 走到 local latest，于是返回 false。

建议流程：

1. 读取 remote ref。
2. fetch/stage remote head 及其 parent chain。
3. 基于已下载 descriptor 做 fast-forward 判断。
4. 通过后再推进 local ref；冲突时保留 fetched objects 但不修改 ref/workspace。

### E2E-SEC-001：restic 密码与加密仓库存放在同一远端（安全设计风险）

当前实现为了让 fresh clone 自动打开镜像仓库，将 restic 密码写入：

```text
projects/<project>/objects/restic-password
```

该文件与加密 restic repository 位于同一个远端权限域。虽然 SSH 传输和本地文件权限正常，但远端存储一旦泄露，攻击者同时获得密文和解密密码，restic 加密不再提供独立保护。

建议：

- 密码由系统 keychain、用户提供的 secret、SSH agent 派生机制或独立密钥服务分发；
- 如果 v0 暂时接受同域托管，应在设计文档和 CLI 中明确威胁模型，不能宣称远端存储泄露时仍受 restic 加密保护。

## 6. 性能与实现观察

- 逐文件镜像成功解决 snapshot ID 稳定性，但每个文件需要独立 SSH/SFTP 往返；仓库增长后可能产生明显延迟。
- `pushResticObjects` 目前以“远端同路径存在”作为去重条件，没有校验大小或内容。若远端对象截断/损坏，增量 push 不会修复。
- 逐文件合并多个写入者的 restic repository 需要额外并发/CAS 测试；本轮只覆盖串行双机提交。
- 建议下一阶段增加仓库对象 digest/size 清单，并用批量 SFTP session 或 tar/pack manifest 降低往返次数。
